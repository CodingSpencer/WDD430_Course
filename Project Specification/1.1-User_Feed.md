## 1. Problem Statement

Users currently lack an intuitive way to explore and browse active sports groups and scheduled events. Relying solely on explicit search queries requires users to already know what they are looking for, limiting discovery.

Without structured feed filters and browsing options, users cannot easily discover groups matching their specific sport, location, and schedule availability.

The User Feed will provide a centralized discovery experience for active public sports groups and upcoming public events. Users will be able to browse available activities, identify relevant groups at a glance, and filter results based on sport and day of the week.

---

## 2. Goals

* **G-1:** Display a responsive feed of sports groups and upcoming events with key metadata visible at a glance.
* **G-2:** Provide direct links on every feed card to the corresponding full group or event detail page.
* **G-3:** Clearly highlight event/group location and meeting schedule, including day of week and time slot where available.
* **G-4:** Explicitly display the designated sport/activity associated with each group or event.
* **G-5:** Allow users to filter the feed by sport type, day of the week, and geographical proximity where location data is available.

---

## 3. Non-Goals

* **Feed creation/editing:** Creating new groups or scheduling events will be handled under Feature 1.4.
* **Payment processing:** Paid league registration fees, ticket purchases, and other payment flows are out of scope for this version.
* **Chat/messaging:** Direct messaging from feed cards is handled separately under Feature 2.0.
* **Algorithmic social feeds:** The feed will not implement social engagement scoring such as likes, comments, or popularity rankings.
* **Personalized recommendations:** Machine-learning-based recommendations are not part of this implementation.
* **Private group discovery:** Private or hidden groups will not appear in the public feed.

---

## 4. Personas & User Stories

### Casual Athlete / Student

> As a casual athlete or student, I want to browse local sports groups filtered by day of the week and sport so that I can find a pickup game that fits my open schedule.

### Self-Learner / Player

> As a player, I want to click on a feed card to open its detail page so that I can learn about skill-level requirements, rules, location, and schedule before requesting to join.

### Group Organizer / Admin

> As a group organizer or admin, I want my created groups and events to appear automatically in the public discovery feed so that new players in my area can find us.

## 5. Functional Requirements

Requirements use RFC 2119 terminology: **MUST**, **SHOULD**, and **MAY**.

### Feed

**FR-1:** The system MUST render a paginated or infinite-scrolling feed combining active groups and upcoming public events.

**FR-2:** The feed MUST exclude archived, private, hidden, deleted, or otherwise unavailable groups/events at the database query level.

**FR-3:** Each feed item MUST represent exactly one group or event and contain a stable identifier that can be used for navigation.

### Feed Cards

**FR-4:** Each feed item card MUST visually display:

* Title
* Sport/activity category
* Location name, city, or facility
* Meeting day(s) of the week
* Group/event thumbnail image or fallback image
* Event/group type where applicable

**FR-5:** If a specific meeting time is available, the feed card SHOULD display the meeting time.

**FR-6:** Missing images MUST fall back to a default image associated with the sport/activity category.

### Filtering

**FR-7:** The system MUST provide a filter control for **Sport** using multiselect functionality.

**FR-8:** The system MUST provide a filter control for **Day of Week** using multiselect functionality.

**FR-9:** The system SHOULD provide a geographical proximity filter when location information is available.

**FR-10:** Applying or removing a filter MUST update the displayed feed without requiring a full-page reload.

**FR-11:** Users MUST be able to clear all active filters through a single reset action.

### Navigation

**FR-12:** Clicking or tapping anywhere on a feed item card MUST navigate the user to the corresponding Group Detail or Event Detail page.

**FR-13:** Navigation MUST preserve the selected feed filters when the user returns to the feed where supported by the client application.

### Sorting

**FR-14:** The system SHOULD automatically order feed results by geographical distance relative to the user's selected market location.

**FR-15:** When geographical distance is unavailable, the system SHOULD fall back to chronological ordering based on the next scheduled meeting/event date.

**FR-16:** The system MAY display a **New** badge on groups created within the previous 14 days.

### Pagination

**FR-17:** The API MUST support pagination or cursor-based retrieval.

**FR-18:** A standard feed request SHOULD return no more than 20 items.

## 6. Non-Functional Requirements

### Performance

* Feed API requests MUST achieve **p95 < 150 ms** for standard payloads of 20 items under normal application load.
* Filter requests SHOULD update the client-visible results within **300 ms** when data is already available through the application's API/cache layer.
* Database queries MUST use appropriate indexes for the primary feed access patterns.

### Security

* Public feed items MUST be accessible to unauthenticated visitors.
* Private, hidden, archived, and deleted groups MUST be filtered at the query/service layer rather than relying solely on frontend visibility controls.
* API responses MUST NOT expose private group information.
* User-specific location information MUST NOT be exposed to other users unless explicitly required by the product.

### Accessibility

* The feature MUST comply with **WCAG 2.1 AA**.
* Feed cards MUST support keyboard navigation.
* Interactive controls MUST have accessible names.
* Screen readers MUST be able to identify each card's title, sport, location, schedule, and navigation destination.
* Focus order MUST follow the visual reading order.

### Scalability

* The feed is expected to be a read-heavy workload.
* Feed queries MUST use appropriate composite indexes.
* The primary group feed query SHOULD utilize an index covering `(market_id, status, sport_id)`.
* Pagination SHOULD use cursor-based pagination if offset pagination becomes a performance bottleneck.

### Reliability

* The feed service MUST target **99.9% availability**.
* Missing card images MUST fall back gracefully.
